A **plugin** is a stateful, long-running integration. Plugins hold
credentials, maintain connections, expose typed methods, and are the
only Gibson component kind that can read secrets at runtime.

Reach for a plugin when you need to:

- talk to a stateful backend (Shodan, Splunk, Vault, your CRM)
- maintain a long-lived session (browser automation, persistent SSH
  pool)
- reuse expensive setup across many calls (loaded ML model, warm cache)
- safely handle credentials that should never reach an agent

If the work is stateless and contract-shaped, "given X, return Y" -
build a [tool](/docs/tools) instead.

## Two runtimes, one component kind

Every plugin is the same component kind, with the same enrollment, secret
bindings, permissions and lifecycle. What differs is the **runtime**, which
decides where the method implementations come from:

| Runtime | You write | Reach for it when |
|---|---|---|
| `code` (default) | The methods themselves, in a binary that calls `plugin.Serve(ctx)`. | The integration does not exist yet, or you need behaviour a vendor server does not offer. |
| `mcp-bridge` | Nothing. You point at an existing [Model Context Protocol](https://modelcontextprotocol.io) server and it runs **unmodified**. | A vendor already ships an MCP server for the system you want to reach. |

A plugin on the `mcp-bridge` runtime is called a **connector**. That is a
name for a configuration, not a second component: there is no connector
runtime, no `gibson connector` command, and nothing in this page that stops
applying to it. Everything below is true of both unless a section says
otherwise.

## Plugin shape

A plugin is:

- a **`plugin.yaml`** manifest at the root of your plugin directory
- a binary that calls `plugin.Serve(ctx)`
- registered with `gibson component register --kind plugin --token <bootstrap>`
- invoked **by tools**, not directly by agents, see
  [Roles & permissions](/docs/rbac#plugin-invocation).

## Scaffold a new plugin

```bash
gibson component init --kind plugin --dir ./my-plugin
```

The CLI generates a working starting point:

| File | Purpose |
|---|---|
| `plugin.yaml` | Manifest. Edit this to declare your methods and secrets. |
| `main.go` | Entry point, calls `plugin.Serve` with an Echo handler. Replace with your own. |
| `<name>.proto` | Sample request/response messages. Edit, then `make proto`. |
| `Makefile` | Targets: `proto`, `build`, `enroll`, `run`. |
| `Dockerfile` | Multi-stage build, suitable for `runtime: pod`. |
| `.gitignore`, `README.md` | Boilerplate. |

Names must match `^[a-z][a-z0-9-]{0,61}[a-z0-9]$` (DNS-label style).

Validate the manifest before you register:

```bash
gibson component validate
```

## The `plugin.yaml` manifest

```yaml
apiVersion: plugin.gibson.zeroroot.ai/v1
kind: Plugin

metadata:
  name: my-shodan
  version: "0.1.0"
  description: Shodan host lookup
  author: you@example.com

spec:
  workload_class: plugin
  runtime: process              # process | pod | setec  (default: process)

  policy:
    setec_required: false       # if true, force runtime to "setec"

  secrets:
    - name: cred:shodan_api_key
      scope: per_call            # startup | per_call
      rotation: live             # live | restart
      required: true

  methods:
    - name: lookup_host
      description: Look up a host on Shodan.
      request_proto:  myorg.shodan.v1.LookupRequest
      response_proto: myorg.shodan.v1.LookupResponse

  health:
    startup_timeout:    30s
    liveness_interval:  10s

  egress:
    - host: api.shodan.io
      protocol: https
      port: 443
      purpose: Shodan API calls
```

### Runtime modes

| Mode | Where the plugin runs | Pick this when |
|---|---|---|
| `process` (default) | Bare process, laptop, VM, sidecar container | Fastest dev loop, simplest deploy. |
| `pod` | A Kubernetes pod, scheduled by your runtime of choice | Production-style isolation. The included `Dockerfile` is wired for this. |
| `setec` | A microVM under the [Setec](https://github.com/zeroroot-ai/setec) sandbox operator | Strong isolation for sensitive workloads. `policy.setec_required: true` forces this. |

### Secret declarations

Each entry in `spec.secrets` declares a credential the plugin needs:

| Field | Values | Effect |
|---|---|---|
| `name` | e.g. `cred:shodan_api_key` | Stable identifier the plugin requests at runtime. |
| `scope` | `startup` \| `per_call` | `startup`: read once at boot. `per_call`: re-read on each method invocation (subject to a small cache). |
| `rotation` | `live` \| `restart` | What the plugin does when the secret rotates, see below. |
| `required` | `true` \| `false` | If `true`, the plugin fails to start when the secret can't be resolved. |

Bindings are created at register time in the deploy wizard. Your
plugin's identity is granted access to **exactly the secrets it
declared** and nothing else. See
[Secrets management](/docs/secrets-management) for the operator side.

### Egress declarations

`spec.egress` is an explicit list of the outbound network destinations
your plugin will dial. It documents the plugin's network footprint for
review and is enforced where the runtime supports it (e.g. Setec).

## Register and run

After the dashboard's deploy wizard, you have a single-use **bootstrap
token** (default 1 hour, configurable up to 24 hours).

```bash
gibson component register --kind plugin --token eyJ...

# verify
gibson inspect --kind plugin

# run
gibson component run
```

`register` exchanges the bootstrap token for a persistent **Ed25519
host key** at `~/.gibson/plugin/<name>/host_key` (mode `0600`). The
host key is what the plugin uses for the rest of its life, the
bootstrap token is consumed and discarded.

`gibson component run` is equivalent to running your built binary, which
calls `plugin.Serve(ctx)`. `Serve`:

1. Loads and validates your manifest.
2. Loads the host key.
3. Registers with Gibson.
4. Calls your `OnStart` hook once the platform marks the install
   `Ready`.
5. Polls for work, dispatches handlers, and submits results.
6. On `SIGTERM`/`SIGINT`, drains in-flight work, calls `OnStop`,
   exits.

## Calling a plugin

Plugins are invoked through a tool's harness:

```go
out, err := h.QueryPlugin(ctx, "my-shodan", "lookup_host", req)
```

Only **tools** can invoke plugins. Agents go through a tool when they
need a plugin's capability, this keeps the agent path free of
credential-bearing code paths and gives you a single point to gate
plugin invocations from. See
[Roles & permissions](/docs/rbac#plugin-invocation).

## Reading secrets at runtime

The plugin SDK exposes a secrets client:

```go
val, err := secretsClient.Resolve(ctx, "cred:shodan_api_key")
```

Internally:

1. The client checks that the requested name is in your manifest's
   `spec.secrets` list, anything else never hits the wire.
2. The cache is consulted (default 60-second TTL, max 1 hour).
3. On a miss, Gibson resolves the value through your tenant's
   configured **secrets backend** (the built-in encrypted store, or
   your own Vault / AWS Secrets Manager / GCP Secret Manager / Azure
   Key Vault). See
   [Secrets management](/docs/secrets-management).

Credential **values never appear in audit logs**, only the secret
name and the requesting plugin identity.

## Rotation

When an admin rotates a secret, Gibson notifies your plugin. Behaviour
follows your manifest:

| `rotation` | Plugin behaviour |
|---|---|
| `live` | Cache entry invalidated. Next `Resolve` fetches the new value. No restart. |
| `restart` | Plugin stops accepting new work, drains in-flight handlers, calls `OnStop`, and exits. Your runtime (Kubernetes, systemd, …) restarts the plugin, which picks up the new value on the next start. |

`live` is the right default for most rotations. `restart` is useful
when your plugin caches derived state from the credential (e.g. a TLS
client built from a cert + key) and you'd rather rebuild the whole
plugin than try to invalidate that derived state mid-flight.

## Lifecycle states

The plugin's status in your tenant transitions through:

```
Registered → Enrolled → Ready → (Draining → Restart) → Terminated
```

| State | Means |
|---|---|
| **Registered** | The deploy wizard finished and a bootstrap token was issued. |
| **Enrolled** | The plugin host has exchanged the token for a persistent host key. |
| **Ready** | The plugin connected, registered methods, and passed startup health. |
| **Draining** | A rotation-restart is in flight, or an admin issued a stop. |
| **Terminated** | The plugin exited cleanly. |

The dashboard's plugin list shows the current state plus uptime and
recent invocation counts.

## Permissions summary

| Action | Granted to |
|---|---|
| Resolve a bound secret at runtime | The plugin's own identity (manifest-bound, no broader). |
| Invoke a plugin method | A tool with a `can_invoke` grant for that plugin, or a tenant member. |
| Register / configure / delete a plugin | Tenant admins. |

See [Roles & permissions](/docs/rbac).

## Connectors

A **connector** is a plugin on the `mcp-bridge` runtime. It brings an existing
MCP server into Gibson without rewriting it or porting its tools: the vendor
server runs unmodified behind a generic bridge, and its tools become callable
inside your missions.

"Unmodified" is literal. Gibson never forks, patches or wraps a vendor server.
The bridge is an ordinary **MCP client**: it performs the `initialize`
handshake, discovers what the server offers with `tools/list`, registers those
as the connector's methods, and forwards each call as `tools/call`. The vendor
server has no idea Gibson exists. That is why one runner image serves every
connector and there is no per-connector build.

What the bridge handles for you:

- spawning or connecting to the vendor MCP server,
- the MCP `initialize` handshake and `tools/list` discovery,
- resolving the secrets the vendor server needs from
  [Gibson-managed secrets storage](/docs/secrets-management),
- exposing each discovered tool to your agents and missions.

### Two transports, and where the vendor server runs

A connector reaches its vendor MCP server one of two ways. The difference is
not only mechanical: **it decides whether any vendor code runs in your
infrastructure at all.**

| Transport | When | How | Where the vendor server runs |
|---|---|---|---|
| `stdio` (default) | The vendor server is a local executable (an `npx`/`uvx` package, a binary). | The bridge spawns it as a subprocess and speaks MCP over stdin/stdout. | **In your infrastructure**, as a child process of the bridge. |
| `http` | The vendor server already runs as a network service. | The bridge connects to its base URL. | **Somewhere you or the vendor already operate.** Nothing of theirs runs in your cluster. |

#### `http` runs no vendor code

With `http`, the MCP server is a service that already exists. GitLab's, for
example, is a feature of your own GitLab instance at
`https://<your-gitlab>/api/v4/mcp`. The bridge makes outbound calls to it as a
client. There is no vendor package to install, no subprocess, and nothing
third-party executing next to your workloads.

Authenticate with `spec.mcp_bridge.auth`, which presents a credential resolved
from Gibson-managed secrets as a request header:

```yaml
spec:
  mcp_bridge:
    transport: http
    endpoint: https://gitlab.example.com/api/v4/mcp
    auth:
      type: bearer
      secret: cred:gitlab-access
```

#### `stdio` runs the vendor's code, where you decide

With `stdio`, the bridge spawns the vendor server, so third-party code executes
inside the bridge's execution context. **Which context that is comes from the
connector's `runtime`**, exactly as it would for a code plugin:

| `runtime` | Where the vendor subprocess ends up |
|---|---|
| `process` | Beside the bridge, in the same process space. |
| `pod` | In a Kubernetes pod. |
| `setec` | In a [Setec](https://github.com/zeroroot-ai/setec) microVM, with the connector's declared `spec.egress` enforced at the microVM boundary. |

If you are bridging a package you did not write — most `npx`-distributed MCP
servers — `setec` is the runtime to choose, and `policy.setec_required: true`
makes that non-negotiable for the component.

### Scaffold a connector

A connector is scaffolded with `gibson component init`, the same command
that scaffolds any component, with `--kind plugin --runtime mcp-bridge`.
It writes a `plugin.yaml` whose `spec.mcp_bridge` block describes the
vendor reference, the transport, and the secret-to-environment-variable
mapping the vendor server expects. (There is no separate `gibson
connector` command, a connector is just a plugin with the mcp-bridge
runtime.)

```bash
# stdio: spawn an npm-published MCP server as a subprocess
gibson component init github-bridge --kind plugin --runtime mcp-bridge \
  --command npx --arg=-y --arg=@modelcontextprotocol/server-github \
  --secret github_token=GITHUB_PERSONAL_ACCESS_TOKEN

# http: bridge an already-running MCP server
gibson component init internal-api --kind plugin --runtime mcp-bridge \
  --transport http --endpoint https://mcp.example.com/mcp
```

| Flag | Notes |
|---|---|
| `--kind plugin` | Required, a connector is a plugin. |
| `--runtime mcp-bridge` | Selects the connector (MCP-bridge) scaffold instead of a code plugin. |
| `--transport` | `stdio` (default) or `http`. |
| `--command` | stdio: the executable that runs the vendor server (e.g. `npx`, `uvx`). |
| `--arg` | stdio: one argument to `--command`, repeatable and ordered. |
| `--endpoint` | http: the base URL of the running vendor server. |
| `--secret` | A `<broker-name>=<ENV_VAR>` mapping, repeatable. The bridge resolves the broker secret and injects it as the named environment variable. |
| `--force` | Overwrite existing files. |

### Validate and run locally

Because a connector is a plugin, it uses the same local component
commands, no connector-specific verbs:

```bash
gibson component validate   # schema + proto checks against plugin.yaml
gibson component run        # run the mcp-bridge locally in this directory
```

`gibson component run` runs the bridge with declared secrets resolved
from **your environment** rather than the platform secrets broker, so you
can iterate without a daemon. Set the environment variables named in your
`--secret` mappings first, e.g. `export GITHUB_PERSONAL_ACCESS_TOKEN=...`.

### Deploy it

Once `gibson component run` starts the bridge cleanly against your vendor
server, the connector deploys like any other plugin:

1. Enroll a plugin identity and register it with `gibson component
   register`, see [Component bootstrap & auth](/docs/component-bootstrap).
   The connector's `--kind` is `plugin`.
2. Bind the vendor server's secrets to the plugin so the bridge resolves
   them from Gibson-managed secrets storage instead of your shell, see
   [Secrets management](/docs/secrets-management).
3. Reference the bridged tools from a mission the same way you reference
   any tool.
